# Chat Customizations Evaluations 插件原理分析

> 开源仓库：[microsoft/vscode-chat-customizations-evaluation](https://github.com/microsoft/vscode-chat-customizations-evaluation)（MIT 协议）

---

## 整体架构

采用标准 **LSP（语言服务器协议）** 架构，分为客户端和服务端两部分：

```
VS Code 扩展客户端 (client/)
        ↕ LSP 协议
语言服务器 (src/server.ts)
        ↓
LLM 分析器 (src/analyzers/llm.ts)
        ↓
GitHub Copilot API（通过 vscode.lm 代理转发）
```

### 目录结构

| 目录/文件 | 职责 |
|---|---|
| `client/src/` | VS Code 扩展宿主，负责启动语言服务器、转发 LLM 请求、注册命令和状态栏按钮 |
| `src/server.ts` | LSP 语言服务器，接收分析请求，调用 LLM 分析器，推送 Diagnostics |
| `src/analyzers/llm.ts` | 核心分析逻辑，构造 Prompt、调用 LLM、解析 JSON 结果 |
| `src/types.ts` | 共享类型定义 |

## 核心机制

### 1. 单次 LLM 调用覆盖全部分析维度

最关键的设计决策：将 5 种分析**合并成一个 LLM 请求**，要求 LLM 返回结构化 JSON，避免多次网络往返：

```
analyzeCombined()
  → 构造包含所有分析指令的超长 System Prompt
  → 将文档内容包裹在 <DOCUMENT_TO_ANALYZE> 标签中
  → 要求 LLM 返回：
    {
      contradictions: [...],       // 矛盾检测
      ambiguity_issues: [...],     // 歧义分析
      persona_issues: [...],       // 人格一致性
      cognitive_load: {...},       // 认知负荷
      coverage_analysis: {...},    // 语义覆盖
      custom_diagnostics: [...]    // 自定义诊断（可选）
    }
  → 解析 JSON → 转换为 VS Code Diagnostic 对象
```

### 2. 并行执行两个分析阶段

```typescript
const phases = [
  { name: 'combined',              promise: this.analyzeCombined(doc) },
  { name: 'composition-conflicts', promise: this.analyzeCompositionConflicts(doc) },
];
const settled = await Promise.allSettled(phases.map(p => p.promise));
```

- **`analyzeCombined`**：对当前文件做全量分析（5 个维度 + 自定义诊断）
- **`analyzeCompositionConflicts`**：读取当前文件 Markdown 链接引用的其他 `.prompt.md` / `.agent.md` / `.instructions.md` 文件，拼接成组合文本，再发一次 LLM 请求检测跨文件冲突

### 3. 精确定位诊断位置

LLM 返回的是**原文片段**（如 `"exact text from the prompt"`），插件使用 `findTextRange()` 在文档中定位该文本：

1. 先做精确子串匹配（大小写不敏感）
2. 失败则回退到关键词匹配（取前 5 个长度 > 3 的词）
3. 最终得到精确的行列号，输出到 VS Code Problems 面板

### 4. GitHub Copilot 代理机制

插件不直接持有 LLM API Key，而是通过 LSP 自定义请求将调用转发给客户端：

```
语言服务器
  → connection.sendRequest('chatCustomizationsEvaluations/llmRequest', ...)
      ↓
VS Code 扩展客户端
  → vscode.lm API（GitHub Copilot）
      ↓
  → 返回 LLM 响应文本
```

用户只需登录 GitHub Copilot，无需任何 API Key。

### 5. 防提示词注入设计

- 被分析的文档内容用 `<DOCUMENT_TO_ANALYZE>` XML 标签包裹，与分析指令物理隔离
- 拼接跨文件组合文本前，会剥离链接文件中已有的 `<DOCUMENT_TO_ANALYZE>` 标签，防止链接文件通过边界欺骗劫持系统提示词
- 总拼接大小上限为 **100,000 字符**，超出则截断

### 6. JSON 解析容错

LLM 输出可能包含 Markdown 代码块包裹（` ```json ... ``` `）或首尾散文，`extractJSON()` 会：

1. 剥除 Markdown 代码栏
2. 从第一个 `{` 到最后一个 `}` 切片，容忍首尾杂文
3. 解析失败则在 Problems 面板输出 `llm-parse-error` 诊断提示用户重试

## 数据流全景

```text
用户点击 "Analyze Prompt"
        ↓
client/extension.ts：注册命令，发 LSP 请求 analyzeDocument
        ↓
src/server.ts：收到请求，取出当前 TextDocument，调用 runFullAnalysis()
        ↓
src/analyzers/llm.ts：并行执行 analyzeCombined + analyzeCompositionConflicts
        ↓
两次（或多次）LLM 调用（经 client 代理转发给 Copilot）
        ↓
解析 JSON → 调用 findTextRange() 定位每条问题的行列号
        ↓
resultsToDiagnostics() 转换为标准 Diagnostic 对象
        ↓
connection.sendDiagnostics() 推送到 VS Code Problems 面板
```

## Waza 集成（评估框架）

除 LLM 分析外，插件还集成了 **waza** 评估工具（Go 编写），用于对 Skill 文件运行结构化评估：

- `waza new eval <skill-name>`：生成 eval.yaml 脚手架
- `waza run <eval.yaml> --context-dir <dir>`：执行评估套件
- 若 `waza` 不在 PATH 中，自动尝试从同级目录 `go run ./cmd/waza` 回退执行
